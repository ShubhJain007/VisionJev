## 2. The gap to the top, item by item

B2 answers 186 of 231 public items. **Passing 86.6% needs 201: +15 items.** 88% needs +18, 90% needs +22.
All but 3 of the 45 misses are in the hard tier:

| Family (tier) | Wrong / items | What the missed items need (read from the items' own rationales) |
|---|---|---|
| temporal_numeric (hard) | **12 / 15** | 3–4 chained steps: month-end rule + leap year + time-zone conversion + deadline comparison; business-day counts across closures |
| judge_hard (hard) | 8 / 17 | verify a fluent worked answer that hides one wrong step (e.g. a final addition off by one unit); rubric caps |
| multi_hop (hard) | 7 / 18 | entity resolution (vendor alias → id), then FX conversion, then an aggregation window, then a threshold table |
| long_policy (hard) | 6 / 19 | 2,000-token policies with an amendment or exception that overrides the obvious clause |
| probability (hard) | 3 / 10 | conditional / complement / expected-value computations stated in prose |
| tradeoff (hard) | 3 / 6 | eliminate options on hard constraints first, then rank the survivors on the stated priority |
| adequacy (original) | 3 / 12 | does a response satisfy every explicit requirement |
| adversarial (hard) | 2 / 6 | injected instructions, misleading summary notes |
| ambiguous (hard) | 1 / 7 | — |

Three observations shape the plan:

1. **27 of the 45 misses are computation chains** (temporal_numeric, multi_hop, probability, the arithmetic half of
   judge_hard). A single forward pass of a 4B model has to carry three or four intermediate values with no scratch
   space. Data alone moved temporal_numeric from 13% to 20%. This is a depth problem, so §4 adds a scratch step.
2. **The errors are not confidently wrong everywhere.** On multi_hop and half of temporal_numeric the top probability
   on a miss is 0.24–0.54, so the model knows it is unsure. That is what makes think-if-unsure cheap: the extra work
   runs only where the first pass is unsure.
3. **judge_hard misses are confident** (0.51–0.86): the model accepts fluent answers. That needs data where a fluent
   answer is wrong in exactly one step (§3.2), not more thinking alone.

Targets for round 3: **JevBench public ≥ 87.0, hard ≥ 72**, ECE ≤ 0.05, no regression > 1 point on zero-shot,
never-seen, held-out wording. Stretch: 90 (+22 items).

## 3. Track A: data that closes the JevBench gap (all exact labels, CPU only)

### 3.1 Compound exact generators (`visionjev_gen3.py`)

Every item carries a worked rationale **with the intermediate values**, a withheld-input variant (CBD) at ~5%, rank-uniform
numeric options and mistake distractors that are the result of one specific wrong step (so each distractor names a
real failure: used 28 Feb, forgot the time zone, aggregated the wrong vendor).

| Family | Composition (each factor sampled independently) | JevBench family it targets |
|---|---|---|
| `gen_deadline_chain` | month arithmetic with month-end rule × leap year × two time zones (DST included) × "by end of day" / "within N hours" × business-day roll | temporal_numeric |
| `gen_period_count` | inclusive / exclusive counting × closures × part-days × notice received after cut-off counts next day | temporal_numeric |
| `gen_fx_aggregate` | alias → entity id table × several invoices in two currencies with dated rates × rolling window × approval-tier table × a look-alike entity that must not be aggregated | multi_hop |
| `gen_lookup_chain` | 3–4 hop joins across tables in one long state (employee → cost centre → policy class → limit) with one superseded row | multi_hop, long_policy |
| `gen_cond_probability` | two-stage events, complements, "at least one", expected value with a fee; prose only, fractions and percents mixed | probability |
| `gen_constraint_rank` | options × hard constraints (some hidden in a handling note that contradicts the label) × a priority order × a tie-break | tradeoff |
| `gen_amended_policy` | base policy + amendment with effective date + exception + a summary note that contradicts the clause; 2–3.5k tokens | long_policy, adversarial |

### 3.2 Judge sets with planted single-step errors (`visionjev_judge_gen.py`)

Take any generator item and its worked rationale, then write a *response* in fluent prose: either the correct chain, or
the same chain with exactly one corrupted step (one-unit addition slip, wrong rate date, skipped exception, right
method with a copied digit wrong). Questions: "Is the response fully correct?" (noul), "Which response is correct?"
(pair), rubric score with caps ("any numeric error caps the score at 2"). Labels are exact because we planted the
error; the fluent wrapper comes from templates plus an open-weight paraphraser (licence as in teacher-lite), never
from a closed model. Also for adequacy: requests with N explicit requirements and responses that satisfy N or N−1.

### 3.3 Teacher round 2, filtered by the student

Same pipeline as teacher-lite (writer → blind thinking answerers → reasoned + one-pass distributions), with three
changes from what round 1 taught us (PROBLEMS D16, E12; teacher_hard was already 80% before training):

- **Keep a question only if `qwen4b-v6b2` gets it wrong or is unsure (top prob < 0.7).** Expected keep rate ~30%, so
  write ~3× more and train on the part that teaches.
- **Evolve instead of only write:** for questions the student solves, the writer adds one step (an amendment, a second
  currency, a decoy clause) and the answer must stay determined. Two rounds.
- **State kinds, not only documents:** tickets and chat threads, tool / agent traces, code and diffs, JSON app state,
  tables, logs, schedules, plus the image kinds of §5. Writer prompt asks for equal-length options and balanced yes / no.
- Rescue contested questions: 5 samples per answerer with a larger thinking budget, plus a third family; keep on ≥ 80%
  majority with vote shares as the soft target.

## 4. Think-if-unsure (the scratch step)

**Why:** observation 1 and 2 above. Imajev ships the same idea ("think if unsure": up to 256 thought tokens when the
single-pass answer is below a threshold, decision read right after the thought).

**How it fits our model.** The rationale loss already trains the backbone to continue `… <options> Because: ` with a
worked rationale. So the generator exists; what is missing is a read-out that can use it.

- **Pass 1:** the normal single pass. If the top probability ≥ τ (start τ = 0.7), return it. Nothing changes for easy
  traffic: same latency, same calibration.
- **Pass 2 (unsure only):** generate ≤ 160 tokens of working after `Because: `, then re-run the read-out with the working
  placed in the state as a `notes` field.
- **Training so the read-out uses notes critically:** the notes must be the *student's own* generated working, right
  or wrong, with the gold label; never the gold rationale (that would teach blind trust and leak the answer). Build
  by running the current checkpoint over ~60k training rows (≈ 1 h on an H100), then train with `notes` present on
  50% of rows. Rows whose notes reach the wrong answer teach the read-out to check the working against the state.
- **Working quality:** raise the rationale cap from 96 to 192 tokens and require intermediate values in every
  generator rationale (§3.1), so the generated working actually computes.
- **Cost control:** report accuracy, latency and the think rate at τ ∈ {0.5, 0.6, 0.7, 0.8}; ship the τ that maximises
  the JevBench composite (it scores speed and cost as well as accuracy), and expose `thinking: off | auto | always`.

This is the largest single lever for the 27 computation misses and is an experiment, not a certainty (H14).

Implemented (b813017): `predict(thinking={"mode": "auto", "threshold": 0.7, "max_tokens": 160})`, greedy generation with
the key/value cache (`generate_continuation`; cached output equals the plain loop in tests, the Qwen path is checked on
the pod by `visionjev_notes.py --selfcheck`), `scripts/visionjev_notes.py` (student notes for training rows),
`--notes-tag` / `--notes-prob` in the trainer, rationales now end with an end-of-text token so generation stops, and
`visionjev_jevbench.py --thinking auto`.

## 6. Track C: agentic trajectories, larger and with a real use test

Round 2 had 2.3k verifier pairs and three sets; only next-action moved (40 → 60%), pairs and outcome stayed near
chance (E12). Changes:

- **More and harder-to-shortcut pairs:** relax the 3-pairs-per-issue cap to 8, allow patches up to 8k chars (the
  4,096-token budget holds ~2 × 5k), add the failing test names from the task to the state, and add pairs from
  `ricdomolm/mini-coder-trajs-400k` once its `verified` flag is confirmed (review running). Target ≥ 15k pairs.
- **Outcome as a value target:** train the existing value head on `agent_outcome` (BCE), at three points of the run
  (25 / 50 / 75%), so it is an early-stop signal and not a second yes / no head.
- **Step progress** (`agent_step_progress`, not built in round 2): steps later reverted, repeated, or followed by the
  same error = no progress; exact from the log.
- **GUI trajectories with screenshots:** AndroidControl next-action and goal-reached (§5.1) are agent tasks too; they go
  in this domain so the agent share covers code and GUI.
- **Tool-call correctness:** given a request, tool schemas and a candidate call, is it correct / which call is
  correct. Reviewed sources are all open-model generated (none human): `nvidia/When2Call` train (CC BY 4.0, 4-way choice
  with rejected answers), `Salesforce/xlam-function-calling-60k` (CC BY 4.0, verified positives) and
  `MadeAgents/xlam-irrelevance-7.5k` (negatives); BFCL and the API-Bank test set stay eval-only. Lower priority than the
  human-labelled tracks.
- **Public rollouts with pass / fail:** no dump fully meets the bar. `mini-coder-trajs-400k` has a `verified` flag (~21%
  true) whose meaning is only inferred, and ~65% of its tasks were written with a closed model (keep `func_pm_*` only);
  OSWorld open-weight runs carry program scores but the card discourages training. AgentRewardBench (human success
  labels, research-only terms) is held out as the judge evaluation. Real pass / fail therefore comes from our own
  open-weight rollouts in the environments listed in §5.1.
- **Own rollouts (optional, ~$15):** run an open-weight coder on SWE-rebench environments, 4 candidates per issue with
  test outcomes: the cleanest pairs, and the data for the use test below.
- **Use test (the point of the track):** best-of-N selection. For held-out issues with ≥ 2 runs, pick one run with the
  verifier (mean of pair wins, or the value head) and report resolved@1 against random choice and against the oracle,
  as CLM's `bon_eval.py` does. Gate: beat random by ≥ 5 points.
- Larger val (300 per set) so these sets can be read; 30 was noise.

### 7.1 Training speed (implemented 2026-09-30, laya-vision b813017)

B2 ran 7 s per step of 16 rows and 75% of the tokens it computed were padding (every batch padded to a ~4k-token
row). Three changes, none of which alters what a step trains on:

- **Length groups** (`--length-groups 4`): each batch of 16 runs as up to 4 forward passes of similar-length rows; the
  outputs are merged back into row order and the loss is computed once over the batch, exactly as before. Same rows,
  same weights, same number of updates. Simulated on mix_v6b2: 3.6× fewer tokens per step; worst step 27k tokens.
  Test: grouped forward equals the padded forward row for row.
- **Checkpointing only when needed** (`--grad-checkpointing-above 30000`): gradients are identical; it was on only to fit
  the padded batches.
- **Two GPUs in one process** (`--devices cuda:0,cuda:1`): the forward passes of a step are spread over the GPUs; the
  second GPU holds a frozen copy and receives the live LoRA / head tensors each step, so there is one optimizer and one
  loss and no multi-process synchronisation. Test: two-device gradients equal single-device gradients.
- Fewer in-training evals (every 500 steps) and one data-validation pass.

Expected for B3's ~72k examples: ~10 h → ~3–4 h on one GPU, ~2 h on two (estimates; `scripts/pod_speedcheck.sh` measures
the real seconds per step, memory and row-for-row equality on the 4B before B3 starts).

- **H17** Verifier trained on ≥ 15k pairs with test names in the state beats random best-of-N by ≥ 5 points resolved@1.

- **H18** Procedural CAD and image-rendered gens raise never-seen vision (88.9%) and do not lower text never-seen.

  held-out wording.

## 10. Risks

- **Fitting the benchmark's style.** We read public items to see what fails; nothing from them is trained on and every
  generated set is linted against them. The sealed set decides the official rank, so gains must show on our own
  held-out families too (H15, H19).
- **Think mode and the composite score.** JevBench scores speed and cost; a high think rate can lose more than it
  gains. The τ sweep decides; single pass stays the default.
- **Student notes cost and quality.** If the 4B's generated working is mostly wrong, pass 2 learns to ignore it. Check
  on 500 rows before generating 60k.
- **Licences.** All four reviews are in (§3.4, §5.1, §5.2, §6). Human-labelled sources come first; model-generated sets are
  supplements only and marked as such.
- **Run length.** 10 h of training is 3× B2; the 500-step evals are the stop signal if val NLL turns.
